If your team is considering automation, the useful starting point is a description of the work people do today. Tell me what arrives, what someone does with it, and where the process becomes slow or unreliable. You can make an initial enquiry before choosing a tool or writing a technical specification.

I work across AI, data engineering, document workflows, and web automation. A project enquiry helps establish whether the problem fits that experience and whether a small, testable first step makes sense. The scope below is a proposed way to begin. Deliverables, availability, fees, and responsibilities need agreement for each engagement.

## What to put in your first message

Describe the current workflow in a few sentences. Include the systems involved, approximate frequency or volume if you know it, and the result you want. Explain what happens when something goes wrong and who has to repair it.

For example, a useful brief could say, “Our team copies invoice totals from supplier PDFs into a spreadsheet. Layouts vary, and someone checks every row before import. We want to test whether extraction can reduce the amount of checking.” This is an illustrative brief, rather than a client result.

A description of document types or a redacted schema is enough to start a conversation. Keep confidential files, credentials, customer records, and regulated data out of the contact form. Access and permitted sample handling can be agreed separately if needed.

## Turn the brief into a question a pilot can answer

A pilot needs a bounded decision. For document extraction, that might be whether required fields can be recovered on a reviewed sample with an acceptable amount of manual correction. For recurring website reports, it might be whether the system detects an introduced failure and delivers an actionable report once.

I would first identify the input, intended output, current baseline, and the person who will assess the result. A dependency such as access to an API or an agreed set of labels belongs in the scope before implementation begins.

## Agree the deliverables before building

A practical scoping note can record the following agreement.

| Scope item | What to make explicit |
| --- | --- |
| Input | Which websites, document families, or systems are included |
| Output | A report, structured records, a working integration, or a review interface |
| Acceptance | What evidence the team needs to make a decision |
| Review | Who checks ambiguous results and how corrections are recorded |
| Boundaries | Excluded formats, integrations, environments, or production responsibilities |
| Handover | Code, configuration, instructions, unresolved issues, and ownership |

Set acceptance criteria before evaluating the final sample. Otherwise it is too easy to adjust the definition of success around the result that happens to appear.

## What the pilot should leave you with

The deliverable should make the next decision easier. A useful handover includes the tested workflow, results and failures, instructions for repeating the evaluation, and a list of dependencies for production. The conclusion may be to proceed, narrow the scope, collect better data, or keep part of the work manual.

Production deployment needs its own agreement on monitoring, access, recovery, running costs, and ongoing support. Discuss these responsibilities when scoping the work so the pilot has a clear endpoint.
